# AI Workflow — 轻量级 AI 工作流可视化编排工具

基于 [BMad Method](https://bmadcodes.com/) + Qdrant + Lark CLI 构建的轻量化 AI 工作流引擎，提供可视化节点编排能力，适合需要快速搭建 AI Agent 工作流的场景，避免 Dify 等重型平台的复杂性。

---

## ✨ 已实现功能

### 1. 可视化工作流编辑器
- **[React Flow](https://reactflow.dev/) 画布** — 节点拖拽、连线、缩放、平移，基于 `@xyflow/react` v12
- **MiniMap** + **Controls** — 小地图导航和画布控制
- **暗色主题** — Ant Design darkAlgorithm + React Flow 暗色适配
- **节点选中高亮** — 选中节点蓝色边框 (`.node_choose`)

### 2. 6 种工作流节点
| 节点类型 | 标识 | 用途 | 编辑面板 |
|---------|------|------|---------|
| **用户输入节点** | `userInput` | 接受用户输入的文本、提示词、文件、URL | 文本/提示词/文件/URL 输入 |
| **智能体节点** | `agent` | 配置 AI 模型、API Key、Token 范围 | 模型 ID、API Key/URL、Token 范围 |
| **BMad 角色节点** | `bmadAgent` | 赋予智能体特定角色（分析师/架构师/SM 等） | 角色、描述、模型、温度、系统提示词 |
| **Lark 文档节点** | `lark` | 读取/写入/创建飞书文档 | 操作类型（读取/写入/创建）、文档 URL、内容 |
| **回答节点** | `answer` | 工作流暂停，等待用户输入 | 问题、预置选项 |
| **AI 输出节点** | `aiOutput` | 展示最终输出结果 | 输出内容（只读） |

### 3. 节点操作
- **添加节点** — 每个节点右侧的 `+` 按钮，下拉选择节点类型，自动生成连线到新节点
- **删除节点** — 编辑面板底部「删除」按钮，同时清理关联连线
- **节点属性编辑** — 右侧 300px 编辑面板，点击节点即切换
- **节点标题/描述编辑** — 编辑面板头部可编辑
- **节点拖拽** — 自由拖拽调整布局

### 4. 执行引擎
- **DAG 执行引擎** — 拓扑排序（Kahn 算法）确定执行顺序，检测循环依赖
- **Pipeline 数据流** — 上游节点 output 自动传递为下游节点 input
- **6 节点执行器** — 用户输入/智能体/BMad 角色/Lark 文档/回答/AI 输出，均有独立执行逻辑
- **智能体节点真实 AI API 调用** — 兼容 OpenAI/Anthropic/Ollama 格式，使用模型管理中配置的 API Key/URL
- **Lark 节点真实 CLI 调用** — 通过 `lark-cli` 子进程执行读/写/创建操作
- **BMad 角色节点** — 接收上游响应，可配置 systemPrompt 进行角色视角 AI 分析
- **Answer 节点暂停/恢复** — 等待用户输入后继续执行
- **孤立节点过滤** — 无连线参与的节点不执行
- **执行控制** — 运行全部/重置，实时状态标签（执行中/已完成/出错/等待输入）
- **执行日志** — 按节点展示 info/warn/error 日志
- **输出面板** — 独立 Tab 展示各节点输出结果，优先展示 AI 输出节点

### 5. 模型管理
- **模型 CRUD** — Table 展示 + Modal 创建/编辑，数据持久化到 `model.conf.json`
- **模型字段** — 名称/描述/模型名/API URL/API Key/Token 范围
- **工作流集成** — 智能体节点编辑面板可选择模型，执行时使用对应配置调用 AI API

### 6. 技能管理（BMad 角色）
- **BMad 角色列表** — 从 `_bmad/config.toml` 解析 agents，Table 展示（图标/角色/名称/团队/描述）
- **工作流集成** — 智能体节点编辑面板可选择角色，选择后自动创建 BMadAgentNode 并连线

### 7. 工作流导入/导出/模板
- **导入** — 弹窗支持粘贴 JSON 或拖拽上传 JSON 文件
- **导出** — 弹窗展示 JSON（可复制）或下载为 `.json` 文件
- **保存模板** — 保存到 `workflows/` 目录，持久化存储
- **工作流管理** — 独立 Tab 页面，列表展示所有已保存模板，支持加载/删除

### 8. 状态管理
- **Zustand** 全局状态管理
- **Immer** 不可变数据更新（`patchCurrentNode`），避免深层 spread
- **NodeBuilder** 工厂模式构建节点，自动生成 UUID 和位置偏移
- **节点连线约束** — 用户输入节点 → 仅能连接智能体节点；智能体节点 → 不可连接用户输入和自身

### 5. 技术栈
- **框架**: React 19 + TypeScript 6 + Vite 8
- **路由**: TanStack Router
- **UI**: Ant Design 6 + Radix UI Icons + Lucide Icons
- **画布**: React Flow 12 (`@xyflow/react`)
- **状态**: Zustand 5 + Immer 11
- **样式**: Sass (SCSS Modules)

## ⚠️ 潜在问题

### 1. 类型安全边界
- `NodeBuilder` 中的 `as any` 类型断言 — `AppNode`（即 `NodeProps<>`）与 React Flow 的 `Node` 类型不完全兼容，节点构造和添加时有多处 `as unknown as Node` 和 `as any` 转换。后续类型收敛后应清理。

### 2. 节点数据深层编辑
- EditItem 组件支持 `inputType: 'text' | 'textArea' | 'password' | 'number'`，但**文件上传**目前仅以字符串路径形式存储，缺少实际文件选择器
- EditItem 的 `value` 类型为 `string | number | File`，但 File 类型的处理尚未实现真实的文件选择 UI

### 3. 连线约束不完整
- `isDisabledNode` 仅定义了用户输入节点和智能体节点的约束规则，其他节点类型（Answer、BMad、Lark、AI Output）暂无条件约束，需根据实际业务流程补充

## 两种运行模式的走向分析

工作流最终将支持 **两种运行模式**：

1. **模式 A：在本系统上直接运行** — 当前已实现的模式，编辑器即运行时
2. **模式 B：导出工作流定义，在其他应用中执行** — 编辑器作为工作流设计器，目标应用（Codex / Cursor / Trae / Claude Code 等）负责执行

以下从多个维度分析两种走向的差异和对后续开发的影响。

### 两种模式对比

| 维度 | 模式 A：本系统运行 | 模式 B：导出到其他应用 |
|------|-------------------|----------------------|
| **运行时** | 本项目内置的 DAG 执行引擎（拓扑排序 + Pipeline 数据流） | 目标应用自身的运行时（Codex Agent / Cursor Rules / 等） |
| **AI Agent** | 需自行维护 AI API 集成（已实现 OpenAI 兼容格式，需持续跟进新模型/新特性） | 目标应用提供 Agent 能力，只需描述模型和提示词 |
| **文件系统** | 已实现本地代码读取（后端 API + 路径安全校验），需维护文件操作逻辑 | 目标应用原生支持文件读写，只需映射路径规则 |
| **外部集成** | 需自行集成 Lark CLI / BMad CLI / Qdrant 等依赖服务 | 需为每个目标平台适配对应的集成方式（或依赖平台自带的集成能力） |
| **执行控制** | 完全可控（可自定义暂停/恢复/重试/并行/超时等） | 受限于目标平台的能力边界 |
| **部署** | 需要部署本系统（前端 + 后端服务） | 零部署成本，导出 JSON 即可使用 |
| **用户群体** | 使用本系统进行开发和调试的用户 | 使用 Codex / Cursor / Trae 等 IDE 的用户 |

### 模式 A 详细分析（本系统运行）

#### 需要继续做的工作

| 模块 | 当前状态 | 后续工作 |
|------|---------|---------|
| **Agent 节点** | ✅ 已实现 OpenAI/Anthropic/Ollama 兼容格式 | 需支持 Tool Calling / Function Calling、流式输出、多模态输入 |
| **执行引擎** | ✅ DAG 拓扑排序 + Pipeline 数据流 | 需实现并行执行（`Promise.all` 分支聚合）、循环重执行（loop body 重新遍历）、条件分支的真正跳转 |
| **错误处理** | ⚠️ 重试节点存在，引擎不支持循环重执行，无超时 | 需实现超时机制、节点级重试循环、异常分支（error 连线）、降级策略 |
| **文件系统** | ✅ 本地文件读取（行范围 + 目录遍历） | 需支持文件写入、文件 diff/对比、Git 操作 |
| **外部集成** | ✅ Lark CLI / BMad CLI / Qdrant 基础集成 | 需持续维护 CLI 兼容性，Qdrant 需实现前端对接和检索 UI |
| **认证与安全** | ❌ 无用户认证 | 需增加 API 鉴权、操作审计、敏感信息加密存储 |
| **监控与日志** | ⚠️ 基础执行日志 | 需增加执行历史、性能分析、耗时统计、调用链追踪 |
| **部署运维** | 本地开发模式 | 需 Docker 化部署、环境变量管理、健康检查、数据备份 |

#### 优势
- 完全掌控执行行为，可以实现任意复杂的编排逻辑
- 可深度集成本地服务（BMad / Lark / 文件系统等）
- 不受外部平台能力限制

#### 劣势
- 需要持续维护一个完整的运行时系统
- 需要自行实现 AI Agent 的高级能力（Function Calling、上下文管理等）
- 用户需要部署和运行本系统

### 模式 B 详细分析（导出到其他应用运行）

#### 需要做的工作

| 模块 | 工作内容 |
|------|---------|
| **工作流 Schema 标准化** | 定义平台无关的工作流 JSON Schema（节点类型、连线规则、数据字段），作为导出合约 |
| **Codex 导出适配器** | 研究 Codex Agent 的配置格式，将工作流节点映射为 Codex 的 agent/skill/context 配置 |
| **Cursor 导出适配器** | 研究 Cursor Rules / .cursorrules 格式，将工作流映射为 Cursor 的 agent 规则 |
| **Trae 导出适配器** | 研究 Trae 的工作流/Agent 格式，进行格式转换 |
| **Claude Code 导出适配器** | 研究 Claude Code 的 tool/agent 配置格式 |
| **节点能力等价映射** | 每个节点类型在目标平台上找到等价实现（Agent → 目标平台的 AI 配置，Code → 文件操作指令，Lark → API 调用指令等） |
| **控制流映射** | 条件分支 / 循环 / 重试等控制流节点在目标平台上的等价表达（部分平台可能不支持） |
| **Schema 版本管理** | 定义 Schema 版本策略，向后兼容 |

#### 优势
- 无需维护运行时，工作流定义即产品
- 用户可在自己熟悉的 IDE 中使用，零学习成本
- 利用目标平台的能力（更好的 AI 模型、插件生态等）

#### 劣势
- 受限于目标平台的能力边界（如不支持条件分支、循环等）
- 需为每个目标平台开发和维护独立的导出适配器
- 平台 API 变更可能导致适配器失效
- 部分平台特定功能（如 Cursor 的 @file 引用）难以泛化

### 关键决策：Agent 能力的归属

两种模式最核心的差异在于 **AI Agent 能力的实现归属**：

```
模式 A:  工作流引擎 → 执行器 → AI API 调用 ← 自行维护 Agent 逻辑
                                                 ↑
                                          需实现: 模型管理、API 兼容、
                                          Tool Calling、上下文窗口管理、
                                          多轮对话、流式输出、Token 计费

模式 B:  工作流 Schema → 导出适配器 → 目标平台运行时 ← 平台提供 Agent 能力
                                                 ↑
                                          需实现: Schema 定义、适配器映射、
                                          能力差异补偿、约束检测
```

### 建议策略：双模式并行

建议采用 **"设计时统一，运行时可选"** 的策略，即：

1. **统一的工作流定义格式** — 无论哪种模式，节点类型、数据字段、连线规则保持一致
2. **模式 A 是本系统的默认运行时** — 提供完整的编辑→执行→调试闭环，适合开发和测试
3. **模式 B 作为补充输出通道** — 工作流设计完成后，可一键导出为目标平台格式
4. **能力降级感知** — 在工作流设计时，提示用户当前设计在目标平台上不可用的能力（例如目标平台不支持并行，设计时给出警告）

### 对后续路线的影响

采用双模式策略后，建议后续路线调整为：

1. **P0** — 完善模式 A 的运行时能力（并行执行、循环重执行、超时机制），这是所有能力的基础
2. **P0** — 定义统一的工作流 JSON Schema（作为模式 B 的导出合约）
3. **P1** — BMad 工作流映射（将画布编排转换为 BMad Method 流程）
4. **P1** — Qdrant 向量检索节点 + 语义检索节点
5. **P2** — 第一个导出适配器（优先 Codex，因其 Agent 配置最接近本项目的节点模型）
6. **P2** — 工作流版本管理
7. **P3** — 更多导出适配器（Cursor / Trae / Claude Code）
8. **P3** — Qdrant 前端完整对接，文档展示 UI
